What it does

Upload a clinical note, then interact with it three ways — all grounded in the note's actual text, all running privately on one machine.

💬

Ask

Ask natural-language questions about a patient's note and get a direct answer — with the exact source snippet it came from.

📋

Summarize

Generate a clean, structured summary of a note: reason for visit, diagnoses, medications, follow-up.

🧬

Extract

Pull structured lists of diagnoses, medications, allergies, procedures, and follow-ups — each verified against the note.

Why it's not just another RAG chatbot

In a clinical setting, an AI that sounds confident but invents a medication or dose is dangerous. This project is engineered for the thing that actually matters: trust.

✅ Verifiable citations

The model cites [n] markers; the pipeline verifies each maps to a real retrieved chunk and drops fabricated ones. Proven adversarially — a made-up citation is rejected while the real one is kept.

✅ Honest refusal

When the answer isn't in the note, it says so and cites nothing — it does not fabricate. Backed by an LLM relevance gate.

✅ Grounded extraction

Every extracted entity carries a verbatim source snippet verified to exist in the note. Unverifiable ones are flagged ⚠ unverified, never silently trusted.

✅ Single-patient safety

Answers default to one selected note; cross-note search is an explicit, clearly-warned opt-in — so answers can't blend different patients.

How it works

A Retrieval-Augmented Generation (RAG) pipeline: find the relevant piece of the note, feed only that to a local LLM, and verify everything against the source.

1

Section-aware chunking

The note is split on clinical section headers (Chief Complaint, Medications, Findings…). Each chunk stores the exact character span it came from — the foundation for verifiable citations.

2

Local embeddings (BGE)

Each chunk is turned into a 768-dim "meaning fingerprint" using a local BGE model — no text leaves the machine.

3

Vector search (Qdrant)

Chunks are stored in a Qdrant vector database, filtered by patient note. A question retrieves the most semantically relevant chunks.

4

Grounded generation (Ollama · Llama 3.1 8B)

A local LLM answers using only the retrieved chunks, cites its sources, and refuses when the answer isn't present.

5

Citation verification

Every citation is checked against the retrieved chunks and resolved to note → section → character span. Fabricated citations are dropped.

Evaluation

Measured on a hand-labeled gold set of 24 Q&A pairs (19 answerable + 5 designed refusal cases). The "gate" is an LLM relevance check that decides whether the note actually contains the answer before responding.

MetricBaselineWith relevance gate (default)
Answer correctness84.2%84.2%
Citation accuracy89.5%89.5%
Retrieval recall@k89.5%89.5%
Refusal on unanswerable Qs60%100%
False-refusal rate0%10.5%
Latency (mean)3.7s5.5s

A measured safety/recall tradeoff. The system initially over-answered questions it should decline (e.g. answering "family history?" from "completed family"). A naive similarity-score threshold was tested and rejected — the score distributions of answerable and unanswerable questions overlap too much. An LLM relevance gate was added instead, lifting refusal from 60% → 100%. Because refusing a real question is safer than fabricating an answer to a fake one, the gate is on by default.

Data & scope

Public data, no PHI

Built on MTSamples public transcription reports plus synthetic demo notes — no credentialing, no protected health information.

Privacy by design

Fully local: embeddings and the LLM run on-device. No clinical text is ever sent to a cloud API.

Honest about limits

Not a medical device — a portfolio project. Summarizes and retrieves what's written; it does not diagnose or advise. Limitations are documented openly.
